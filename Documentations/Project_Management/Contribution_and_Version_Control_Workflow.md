# Contribution and Version-Control Workflow (SCRUM-83)

## 1. Purpose

This document defines the team's GitHub contribution and version-control
workflow for CYBEROPS-07. The goal is to maintain clear contribution
history, protect project artifacts, and provide evidence of individual
team participation.

## 2. Repository Structure

The repository will organize project materials by major artifact and
sprint evidence.

Example structure:

Documentation/
├── Requirements/
├── Network_Foundation/
├── Event_Catalogue/
├── Taxonomy_Triage/
├── Correlation/
├── Playbooks/
├── Project_Management/
└── Final_Report/

Evidence/
├── Sprint_1/
├── Sprint_2/
├── Sprint_3/
├── Sprint_4/
└── Sprint_5/

Packet_Tracer/

## 3. Individual Contributions

Each team member will use their own GitHub account when contributing to
the repository.

Team members will not use a shared account for commits.

Commit history will be used to provide evidence of individual
contributions to the project.

## 4. Commit Guidelines

Commits should:

- Describe the change clearly.
- Reference the relevant Jira issue when practical.
- Represent a meaningful project change.
- Avoid unnecessary or meaningless commits.

Example:

`Add enterprise network addressing plan for SCRUM-74`

## 5. Jira and GitHub Relationship

Jira will be the team's primary task and sprint tracking system.

GitHub will store project artifacts, documentation, configuration files,
testing evidence, and contribution history.

Jira issues should contain links to relevant GitHub artifacts when those
artifacts provide evidence that the work was completed.

GitHub will not duplicate the entire Jira hierarchy.

## 6. Review Process

Work should be reviewed by another team member before being considered
complete when peer review is required.

The person reviewing an artifact should not simply approve their own
work.

Issues identified during review should be corrected and documented.

## 7. Packet Tracer Version Control

Only one team member should modify the master Packet Tracer (.pkt) file
at a time to prevent conflicting changes.

Before modifying the master file, the team member should confirm that no
other member is currently editing it.

Changes to the Packet Tracer file should be documented in the repository.

## 8. Evidence Preservation

Important project evidence should be committed to the repository as soon
as practical after completion.

Evidence should include relevant test results, screenshots, configuration
records, documentation, and other artifacts required to demonstrate
completion.

## 9. Change Control

Significant changes to the approved architecture, requirements, or major
project artifacts should be documented and communicated to the team.

The reason for significant changes should be recorded so that project
decisions remain traceable.

## 10. Contribution Accountability

All four team members are expected to make meaningful technical
contributions in addition to any project-management responsibilities.

GitHub contribution history, Jira assignments, and project artifacts will
provide supporting evidence of individual participation.
